# 프록시(Proxy)

> Agent가 OpenAI API 호출할 때 중간에 로깅하고 싶거나, LiteLLM으로 여러 LLM을 한 엔드포인트로 묶거나, 회사 방화벽 안에서 외부 접속할 때 매번 만나는 게 프록시다. Forward와 Reverse를 구분하는 것만 잡아도 설명이 절반은 끝난다.

관련 문서: [[HTTP_HTTPS]], [[REST_API]], [[WebSocket]], [[DNS]], [[포트]]

---

## 1. 프록시가 뭔데

**Proxy(프록시, 대리인, 클라이언트와 서버 사이에 끼어서 요청을 대신 전달해주는 중간 서버)** 는 말 그대로 "대신 해주는" 서버다.

원래 흐름:

```
Client  ─────────→  Server
```

프록시가 끼면:

```
Client  ─────→  Proxy  ─────→  Server
         (1)            (2)
```

프록시는 (1)을 받아 (2)로 보내고, 서버의 응답을 받아 다시 클라이언트에게 전달.

**비유:** 비서가 대리인. 사장(클라이언트)이 거래처(서버)에 직접 연락하지 않고 비서를 통해 주고받음. 비서가 걸러주거나(필터), 기록하거나(로깅), 여러 사장의 문의를 묶어서 보낼 수(캐시/집계) 있다.

---

## 2. 두 가지 큰 갈래: Forward vs Reverse

이 구분이 프록시 이해의 핵심. **"누구 편에 서 있는가"** 로 갈린다.

### 2-1. Forward Proxy (정방향 프록시)

**클라이언트 편**에 서는 프록시. 클라이언트가 "이 주소로 보내줘"라고 요청하면 대신 나가서 가져온다.

```
[Client A]                       [ google.com ]
[Client B]  ──→  [Forward Proxy] ──→  [ openai.com ]
[Client C]                       [ github.com ]
```

- 서버 입장에선 모든 요청이 프록시에서 오는 것처럼 보임
- 클라이언트가 프록시 주소를 "알고" 설정해야 함 (`HTTP_PROXY=http://proxy.corp:8080`)

**쓰는 곳:**
- 회사 방화벽: 외부 접속 전부 프록시 경유로 강제, 로깅/검열
- 해외 사이트 우회 접속 (VPN과 기능 겹침)
- 광고 차단 / 필터링
- 외부 API 호출 캐시

### 2-2. Reverse Proxy (역방향 프록시)

**서버 편**에 서는 프록시. 외부 클라이언트는 프록시 주소만 알고, 진짜 서버는 뒤에 숨어 있음.

```
                                 [ app server 1 ]
[Client]  ──→  [Reverse Proxy]  ─→  [ app server 2 ]
                                 [ app server 3 ]
```

- 클라이언트는 뒤에 서버가 몇 대 있는지, 어디 있는지 모름
- 프록시 주소가 공인 도메인(`api.example.com`), 뒷단은 내부망 IP

**쓰는 곳:**
- **로드밸런싱(Load Balancing, 부하 분산)**: 여러 서버에 요청 나눔
- **TLS 종료(TLS Termination)**: HTTPS 복호화를 프록시가 맡고 뒷단은 평문 HTTP
- **캐시**: 정적 리소스 캐시로 원본 서버 부담 감소
- **보안 게이트웨이**: WAF(Web Application Firewall), Rate Limiting
- **API Gateway**: LLM 라우팅, 인증, 과금 통합 (LiteLLM Proxy, Kong, AWS API Gateway)

### 2-3. 비교표

| 항목 | Forward Proxy | Reverse Proxy |
|------|---------------|---------------|
| 편드는 쪽 | 클라이언트 | 서버 |
| 클라이언트 설정 | 명시적으로 프록시 지정 필요 | 모름. 그냥 공개 도메인 접속 |
| 숨기는 대상 | 클라이언트의 실제 IP/정체 | 뒷단 서버의 개수/주소 |
| 대표 제품 | Squid, 회사 SOCKS 프록시 | Nginx, HAProxy, Envoy, AWS ALB |
| Agent 개발 관련 | 외부 API 접속 강제 경유 | LiteLLM, vLLM 뒷단, API Gateway |

## 3. 프록시가 하는 일 (기능별)

### 3-1. 캐싱(Caching)

같은 GET 요청 결과를 저장해뒀다가 재사용. `Cache-Control`, `ETag` 같은 [[HTTP_HTTPS]] 헤더로 제어.

### 3-2. 로드 밸런싱(Load Balancing)

- **Round Robin**: 순서대로 뿌리기
- **Least Connections**: 연결 적은 서버에 우선
- **IP Hash**: 같은 클라 IP는 같은 서버로 (sticky session)
- **Weighted**: 서버 성능 차이 반영

### 3-3. TLS 종료(TLS Termination)

HTTPS 복호화를 프록시에서 끝내고, 내부망은 평문 HTTP로 전달. 인증서 관리를 한 곳에서 해결.

```
[Client] --HTTPS--> [Reverse Proxy] --HTTP--> [App]
         (TLS)                      (평문, 내부망)
```

### 3-4. 인증/권한 일괄 처리

각 백엔드 서비스마다 인증을 구현할 필요 없이, 프록시가 JWT 검증 → 헤더로 user ID만 넘겨주면 끝.

### 3-5. 로깅/관찰(Observability)

Agent 개발에서는 LLM 요청/응답을 전부 통과시키는 프록시를 앞에 두고 로그 남기기. LiteLLM, Helicone, Portkey 같은 제품들이 이 패턴.

### 3-6. Rate Limiting(속도 제한)

"IP당 분당 60 요청" 같은 제약. 어뷰징 방지, 비용 통제.

### 3-7. 프로토콜 변환

gRPC ↔ REST, HTTP/1.1 ↔ HTTP/2, WebSocket 업그레이드 처리 등.

## 4. 프록시와 프로토콜 계층

| 계층 | 프록시 종류 | 특징 |
|------|-------------|------|
| L4 (TCP) | L4 LB, 투명 프록시 | 포트/IP만 보고 분배. 빠르지만 HTTP 내용 모름 |
| L7 (HTTP) | Nginx, HAProxy L7, Envoy | URL, 헤더, 쿠키 보고 분배. 라우팅 유연 |

[[포트]] 문서 참고. L4는 TCP 세션 자체를 중계, L7은 HTTP 메시지를 해석 후 재전송.

## 5. 환경 변수와 실제 사용

Python, curl, Git 등 거의 모든 도구가 공통 환경 변수 인식:

```bash
export HTTP_PROXY=http://proxy.corp:8080
export HTTPS_PROXY=http://proxy.corp:8080
export NO_PROXY=localhost,127.0.0.1,*.internal.corp
```

`NO_PROXY`는 "이 주소들은 프록시 거치지 말고 직접 가"라는 예외 목록. 내부 서비스 호출할 때 필수.

Python `httpx`, `requests`는 이 변수를 자동으로 읽는다.

```python
import httpx
client = httpx.Client()   # HTTP_PROXY, HTTPS_PROXY 자동 적용
# 또는 명시적으로
client = httpx.Client(proxies="http://proxy.corp:8080")
```

## 6. HTTPS를 프록시가 어떻게 다루나

### Forward Proxy의 경우: CONNECT 터널

HTTPS는 암호화되어 있어 내용을 못 본다. 그래서 Forward Proxy는 **CONNECT 메서드**로 터널만 만들어준다.

```
Client: CONNECT api.openai.com:443 HTTP/1.1
Proxy:  HTTP/1.1 200 Connection established
(이후 TCP 스트림을 그대로 중계, 내용은 TLS 암호문)
```

프록시는 목적지 도메인만 알 뿐 페이로드는 못 봄. 기업에서 내용까지 검사하려면 **MITM 프록시(TLS Interception, 프록시 자체 CA 인증서를 클라이언트에 설치해 중간에서 다시 암복호화)** 를 써야 함. 보안상 민감.

### Reverse Proxy의 경우: TLS 종료

서버 측이므로 인증서를 직접 가지고 있다. 프록시가 복호화해서 내용 보고, 원하는 로직 적용 후 뒷단으로 전달.

## 7. WebSocket과 프록시

[[WebSocket]]은 `Upgrade: websocket` 헤더로 프로토콜을 바꾼다. 프록시가 이걸 이해해야 한다.

Nginx 예시:

```nginx
location /ws {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 300s;   # 오래 유지되는 연결이라 타임아웃 늘림
}
```

기본값으로 두면 프록시가 60초 후 끊어버려서 "갑자기 연결이 죽어요" 문제가 생김.

## 8. Agent 개발에서 자주 쓰는 프록시 시나리오

### 8-1. LiteLLM Proxy (Reverse Proxy 성격)

여러 LLM 제공자(OpenAI, Anthropic, Bedrock, Azure, 로컬 Ollama)를 한 엔드포인트로 통합. 클라이언트는 `http://localhost:4000` 하나만 보면 됨.

```
                           ┌→ OpenAI
Client ──→ LiteLLM Proxy ──┼→ Anthropic
                           └→ Ollama (로컬)
```

모델명만 바꿔서 `POST /chat/completions` 호출하면 내부적으로 각 공급자 형식에 맞춰 변환.

### 8-2. Helicone / Langfuse / Portkey (Observability Proxy)

LLM 호출을 통과시키면서 토큰, 비용, 지연시간, 프롬프트를 기록. `api.openai.com`을 `oai.helicone.ai`로 바꾸기만 하면 됨.

### 8-3. 회사 방화벽 내 개발 (Forward Proxy)

```bash
export HTTPS_PROXY=http://proxy.corp:3128
export NO_PROXY=localhost,127.0.0.1,internal.corp
```

이 상태로 `openai` SDK가 자동으로 프록시 경유.

### 8-4. 로컬 개발용 Reverse Proxy (Caddy/Nginx)

여러 로컬 서비스에 도메인 붙여 HTTPS로 접근.

```
https://api.local.dev → FastAPI (8000)
https://ui.local.dev  → Next.js (3000)
```

Caddy는 자체 서명 인증서를 자동 생성/설치해줘서 편함.

## 9. 직접 확인

### mitmproxy로 직접 띄워보기

```bash
pip install mitmproxy
mitmproxy                 # TUI
# 또는 GUI
mitmweb
```

환경 변수에 `HTTPS_PROXY=http://localhost:8080` 설정 후 프로그램을 실행하면 mitmproxy 화면에서 요청/응답을 실시간으로 볼 수 있다. Agent 디버깅에 강력.

### Nginx 역방향 프록시 최소 예시

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    location / {
        proxy_pass         http://127.0.0.1:8000;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }
}
```

`X-Forwarded-*` 헤더는 뒷단 앱이 "원래 클라이언트는 누구였는지"를 알게 해주는 관례 헤더. 이걸 안 넘기면 앱 로그에 모든 요청 IP가 127.0.0.1로 찍힌다.

## 10. 왜 이렇게 쓰는가 (트레이드오프)

### 장점
- **관심사 분리**: 앱은 비즈니스 로직만, 인증/TLS/로깅은 프록시가
- **확장성**: 서버 증설/교체를 클라이언트 몰래 진행
- **보안**: 내부망을 외부에 노출 안 함, 공격 표면 축소
- **운영 편의**: 로그, 메트릭을 한 곳에서 수집

### 단점
- **추가 지연(latency)**: 홉 하나 늘어남
- **단일 장애점(SPOF)**: 프록시 죽으면 뒷단 멀쩡해도 서비스 다운
- **디버깅 난이도 증가**: "왜 요청이 도착 안 했지?" 추적 지점이 늘어남
- **헤더 전달 실수**: `Host`, `X-Forwarded-*` 빠뜨리면 앱 로직이 엉킴

## 11. 포함/연결 관계 정리

```
네트워크 구조
 ├─ [[DNS]]          ← 도메인 → IP 해석
 ├─ [[포트]]          ← 어떤 앱 인스턴스가 받을지
 ├─ [[HTTP_HTTPS]]   ← 메시지 포맷
 │   └─ [[REST_API]] ← HTTP의 자원 중심 사용 스타일
 ├─ [[WebSocket]]    ← HTTP에서 업그레이드된 양방향 채널
 └─ 프록시(이 문서)   ← 위 요소들을 중간에서 대신 처리하는 계층
```

## 한마디 요약

프록시는 클라이언트와 서버 사이에서 대신 요청을 전달해주는 서버이고, 클라이언트 편이면 Forward(방화벽/VPN), 서버 편이면 Reverse(로드밸런서/API Gateway)다.
