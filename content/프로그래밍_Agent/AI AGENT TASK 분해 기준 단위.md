**1. "하나의 도구 세트"를 기준으로 자른다** 에이전트가 호출하는 tool/API가 겹치지 않으면 별도 에이전트로 분리. ALL FOR ONE에서 정책·입지·인구 에이전트를 나눈 것도 결국 각자 다른 데이터소스(API)를 쓰기 때문이죠. 도구가 겹치기 시작하면 합치는 게 낫습니다.

**2. "독립 실행 가능 여부"로 자른다** A 에이전트 결과 없이 B가 시작조차 못 하면 → 같은 에이전트(또는 순차 스텝)로 묶고, 병렬로 돌릴 수 있으면 → 별도 에이전트로 분리. 이게 latency 최적화의 핵심이고, ALL FOR ONE에서 7개 에이전트를 병렬로 돌린 이유이기도 합니다.

**3. "프롬프트 역할 충돌"로 자른다** 하나의 시스템 프롬프트 안에 상충하는 지시가 들어가면 성능이 떨어집니다. 예를 들어 "비판적으로 분석하라" vs "친절하게 보고서를 작성하라"는 한 에이전트에 넣으면 둘 다 어중간해지죠. 역할이 충돌하면 분리, 보완적이면 합치는 게 맞습니다.

**실무 체크리스트로 정리하면:**

- 도구/데이터소스가 다른가? → 분리
- 병렬 실행 가능한가? → 분리
- 프롬프트 페르소나가 충돌하는가? → 분리
- 위 3개 다 "아니오"면 → 하나로 합침
