**vLLM 없이 로컬 모델을 쓸 때의 문제점부터 보면:**

일반적으로 HuggingFace transformers로 모델을 로드하면, 요청 하나를 처리하고 → 끝나면 → 다음 요청을 처리합니다. 순차 처리라 느리고, 메모리도 비효율적으로 씁니다.

**vLLM의 핵심 장점:**

**1. 속도 — Continuous Batching** 여러 요청이 동시에 들어와도 하나씩 기다리지 않고 묶어서 처리합니다. ALL_FOR_ONE처럼 7개 에이전트가 병렬로 돌아가는 구조에서는 동시 요청이 많을 텐데, 이때 처리량 차이가 큽니다.

**2. 메모리 효율 — PagedAttention** GPU VRAM을 OS의 가상 메모리처럼 페이지 단위로 관리해서, 같은 VRAM으로 더 큰 모델을 올리거나 더 많은 동시 요청을 처리할 수 있습니다. RTX 4090 24GB라는 제한된 환경에서 특히 중요합니다.

**3. OpenAI 호환 API 엔드포인트 자동 제공** 서버 띄우면 바로 `/v1/chat/completions` 엔드포인트가 생기기 때문에, 기존에 OpenAI나 Grok API를 쓰던 LangChain/LangGraph 코드에서 URL만 `http://localhost:8000/v1`로 바꾸면 끝입니다. 코드 수정이 거의 없어요.

**4. 다중 클라이언트 접속 가능** 한번 서버로 띄워놓으면 여러 프로세스, 여러 에이전트가 동시에 같은 모델에 요청을 보낼 수 있습니다. transformers로 직접 로드하면 이게 까다롭습니다.

**한 줄 요약:** vLLM은 로컬 모델을 "그냥 돌리는 것"에서 "제대로 서빙하는 것"으로 바꿔주는 도구입니다.



**PagedAttention** vLLM의 핵심 기술입니다. LLM 추론 시 KV Cache(이전 토큰들의 계산 결과를 저장하는 메모리)를 OS의 가상 메모리 페이징처럼 블록 단위로 관리하는 방식이에요. 기존에는 최대 시퀀스 길이만큼 메모리를 통째로 예약해야 해서 낭비가 심했는데, PagedAttention은 필요한 만큼만 할당하므로 **GPU 메모리를 훨씬 효율적으로 사용**할 수 있습니다. 그 결과 같은 GPU에서 더 빠르고 더 많은 요청을 처리할 수 있게 됩니다.

**Guided Decoding** 모델이 토큰을 하나씩 생성할 때마다, 다음에 올 수 있는 토큰을 JSON 스키마에 맞는 것들로만 제한하는 기법입니다. 예를 들어 `{"score":` 까지 생성했으면 다음 토큰은 숫자만 허용하는 식이에요. 그래서 **출력이 항상 유효한 JSON이 되도록 강제**합니다. 앞서 논의한 Structured Output의 구체적 구현 방식입니다.

**Continuous Batching** 일반적인 batching은 여러 요청을 모아서 한 번에 처리하되, 모든 요청이 끝날 때까지 기다려야 합니다. Continuous Batching은 **요청이 끝나는 즉시 새 요청을 바로 투입**하는 방식이에요. 보이스피싱 탐지처럼 여러 통화를 동시에 분석해야 하는 상황에서, 한 통화 분석이 끝나면 바로 다음 통화를 GPU에 넣을 수 있어 **처리량(throughput)이 크게 향상**됩니다.
