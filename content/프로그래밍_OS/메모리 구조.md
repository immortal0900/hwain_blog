# 메모리 구조

> AI Agent에서 대용량 임베딩이나 대화 컨텍스트 쌓다가 메모리 누수 터뜨린 적 있어서, 프로세스가 메모리를 어떻게 쓰는지 바닥부터 다시 정리.

## 한 줄 요약
**한 프로세스의 주소 공간은 Code / Data / BSS / Heap / Stack 다섯 영역으로 나뉜다.** 위에서 아래로 쌓인 Stack과 아래에서 위로 자라는 Heap이 중간에서 만나지 않게 설계돼 있다.

## 용어부터

- **가상 메모리(Virtual Memory, 각 프로세스가 독점적으로 쓰는 것처럼 보이는 주소 공간)**: 실제 RAM과 달리 OS가 페이지 테이블로 매핑해주는 가상 주소. 64비트 OS에서 프로세스마다 이론상 16엑사바이트씩 쓸 수 있음.
- **주소 공간(Address Space, 프로세스가 접근 가능한 메모리 주소의 범위)**: 0x0000000000000000 ~ 0xFFFFFFFFFFFFFFFF 같은 범위.
- **세그먼트(Segment, 주소 공간을 용도별로 나눈 구역)**: Code 세그먼트, Data 세그먼트 같은 구분.
- **페이지(Page, 메모리를 관리하는 고정 크기 단위)**: 보통 4KB. OS가 이 단위로 RAM과 디스크를 오가게 함.

## 포함 관계

```
OS 전체 메모리 (RAM + Swap)
 └── 프로세스별 가상 주소 공간 (독립)
      ├── Code 영역 (.text)        ┐
      ├── Data 영역 (.data)        │
      ├── BSS 영역 (.bss)          │  아래쪽 (낮은 주소)
      ├── Heap (↑ 위로 자람)       │
      │       ↕ 빈 공간             │
      ├── Stack (↓ 아래로 자람)    │  위쪽 (높은 주소)
      └── 커널 영역                 ┘
```

**포인트**: 한 프로세스는 반드시 이 5영역을 가짐. [[프로세스 vs 스레드|스레드]]가 여러 개면 Stack만 스레드마다 하나씩 더 생기고 나머지(Code/Data/BSS/Heap)는 공유.

## 5영역 비교표

| 영역 | 저장 내용 | 방향 | 크기 결정 | 생명주기 | 예시 |
|---|---|---|---|---|---|
| **Code (.text)** | 실행 파일의 기계어 코드 | 고정 | 컴파일 시 | 프로그램 전체 | 함수 본체 |
| **Data (.data)** | 초기값 있는 전역/정적 변수 | 고정 | 컴파일 시 | 프로그램 전체 | `int x = 10;` |
| **BSS (.bss)** | 초기값 없는 전역/정적 변수 | 고정 | 컴파일 시 | 프로그램 전체 | `int y;` |
| **Heap** | `malloc`, `new`, 파이썬 객체 | 낮은 → 높은 주소 | 런타임에 증가 | 명시적 해제 or GC까지 | `x = [1,2,3]` |
| **Stack** | 지역변수, 함수 호출 정보 | 높은 → 낮은 주소 | 런타임에 증감 | 함수 반환 시 자동 해제 | `def f(): x = 1` |

## 일상 비유

- **Code = 건물 설계도**: 한 번 찍어내면 안 바뀜. 읽기 전용.
- **Data/BSS = 창고 고정 선반**: 프로그램 시작할 때 이미 배치돼 있음.
- **Heap = 중앙 물류 창고**: 필요할 때 주문해서 받고(malloc), 다 쓰면 반납(free). 정리 안 하면 쓰레기 쌓임(memory leak).
- **Stack = 접시 쌓기**: 함수 호출하면 접시 얹고(push), 반환하면 맨 위 접시 치움(pop). 순서가 엄격.

## Stack vs Heap 차이 (제일 헷갈리는 부분)

| 관점 | Stack | Heap |
|---|---|---|
| **할당 속도** | 매우 빠름 (포인터만 이동) | 느림 (빈 공간 탐색) |
| **할당 단위** | 함수 호출 단위 | 객체 단위 |
| **크기 한계** | 작음 (보통 1~8MB, Windows 기본 1MB) | 큼 (가상 메모리 범위) |
| **접근 패턴** | LIFO (후입선출) | 무작위 접근 |
| **해제** | 자동 (함수 끝나면) | 수동 or GC |
| **단편화** | 거의 없음 | 발생 (오래된 프로세스가 느려지는 원인) |
| **스레드 공유** | 스레드마다 별개 | 공유 |

**스택 오버플로 예시**: 재귀 함수가 무한 호출되면 Stack이 계속 쌓여서 한계 넘음 → `RecursionError` / `Stack Overflow`. 파이썬 기본 재귀 한도는 `sys.getrecursionlimit()` 하면 1000이 찍힘.

## 단계 분해: 파이썬 코드가 메모리 어디에 저장되나

```python
GLOBAL_CONFIG = {"model": "claude"}   # Heap (객체), 참조는 Data

def process(user_input):              # Code 영역
    local_buffer = []                 # 참조는 Stack, 리스트 객체는 Heap
    local_buffer.append(user_input)   # Heap의 리스트에 추가
    return local_buffer               # 반환하면 Stack 프레임 제거
```

### 실행 순서
1. 프로그램 시작 → Code 로드, `GLOBAL_CONFIG` 딕셔너리를 Heap에 생성, 참조를 Data에 저장.
2. `process("hi")` 호출 → Stack에 새 프레임 push, 프레임 안에 `local_buffer` 이름이 생김.
3. `[]` 생성 → Heap에 빈 리스트 객체 생성, 그 주소를 Stack의 `local_buffer`에 저장.
4. `return` → Stack 프레임 pop. Heap의 리스트는 참조 카운트가 유지되면 살아있고, 아무도 안 잡고 있으면 GC 대상.

**주의**: 파이썬에서는 "변수"가 값을 담는 상자가 아니라 **Heap 객체를 가리키는 이름표**다. 정수든 리스트든 전부 Heap에 있음.

## 직접 확인해 보기

### 파이썬 객체 주소
```python
x = [1, 2, 3]
y = x            # 같은 객체
z = [1, 2, 3]    # 다른 객체

print(id(x), id(y), id(z))
# 예: 2547891536960  2547891536960  2547891537024
# x와 y는 같은 Heap 주소, z는 다른 주소
```

### 리눅스/WSL: 실제 메모리 맵 들여다보기
```bash
python -c "import os; print(os.getpid()); input()"
# 다른 터미널에서
cat /proc/<PID>/maps | head -20
```
출력 예시:
```
55a3b8c00000-55a3b8c21000 r--p 00000000 ... /usr/bin/python3   ← Code
55a3b8c21000-55a3b8c6e000 r-xp ...          /usr/bin/python3   ← 실행 가능
55a3b9e00000-55a3ba200000 rw-p 00000000 ... [heap]             ← Heap
7ffc8a700000-7ffc8a721000 rw-p 00000000 ... [stack]            ← Stack
```
**r-xp**는 읽기+실행(Code), **rw-p**는 읽기+쓰기(Data/Heap/Stack).

### Windows: VMMap
Sysinternals의 `VMMap.exe` 실행 → 프로세스 선택하면 Heap, Stack, Image(Code) 영역이 컬러로 표시됨. 실측 사이즈 확인 가능.

### 파이썬 메모리 사용량 추적
```python
import tracemalloc
tracemalloc.start()

huge_list = [i for i in range(10**6)]

snapshot = tracemalloc.take_snapshot()
for stat in snapshot.statistics('lineno')[:3]:
    print(stat)
# 몇 줄에서 몇 MB 썼는지 실시간 확인
```

## AI Agent 개발 관점

| 증상 | 원인 영역 | 해결 |
|---|---|---|
| "대화 길어지면 메모리 계속 증가" | Heap (대화 이력 객체 축적) | 주기적으로 오래된 메시지 drop, 요약 |
| "RecursionError: maximum recursion depth" | Stack | 재귀를 반복문으로 바꾸거나 `sys.setrecursionlimit` |
| "프로세스 RAM이 GB 단위로 튐" | Heap (큰 임베딩/텐서) | `del` + `gc.collect()`, 배치 처리, 스트리밍 |
| "포크한 자식 프로세스가 부모 메모리 복제" | 가상 메모리 COW | [[프로세스 vs 스레드]]에서 자식 적게 띄우거나 `spawn` 사용 |

## 왜 이렇게 5영역으로 나눴나

- **보안**: Code 영역은 **실행 가능 + 읽기 전용**, Data는 **쓰기 가능 + 실행 불가**. 이렇게 분리 안 하면 해커가 Data에 쉘코드 넣고 실행시키는 공격이 가능해짐. 현대 OS의 DEP(Data Execution Prevention)가 이 원칙.
- **효율**: Stack은 LIFO만 허용해서 매우 빠르게 push/pop. Heap은 자유 형식이라 느리지만 유연.
- **공유**: Code 영역은 여러 프로세스가 **같은 물리 메모리를 공유**함. 파이썬 100개 띄워도 인터프리터 코드는 한 번만 RAM에 올라감(페이지 공유).

## 한마디 요약
**Stack은 함수 호출의 접시 쌓기, Heap은 객체 보관 창고. 파이썬 객체는 전부 Heap, 변수 이름표는 Stack에 있다고 기억.**
