# 파일 I/O

> LLM 스트리밍 응답 받을 때 버퍼링 때문에 출력이 뚝뚝 끊기거나, 로그 파일을 async로 썼는데 왜 빨라지지 않는지 의아해서 정리.

## 한 줄 요약
**파일 I/O는 내 프로그램이 직접 디스크를 만지는 게 아니라, 커널에게 "이거 읽어/써 달라"고 부탁하는 시스템 콜이다.** 중간에 커널 버퍼와 유저 버퍼가 끼어 있어서 실제 디스크에 도달하는 시점은 내가 생각하는 것과 다를 수 있다.

## 용어부터 풀이

- **I/O(Input/Output, 입출력, 프로그램이 외부 세계와 데이터를 주고받는 행위)**: 디스크 읽기/쓰기, 네트워크 송수신, 키보드/화면 입출력 전부 포함.
- **시스템 콜(System Call, 유저 프로그램이 커널 기능을 요청하는 공식 통로)**: `open`, `read`, `write`, `close` 같은 것. CPU 모드가 유저 모드에서 커널 모드로 전환됨(비용 있음).
- **파일 디스크립터(File Descriptor, fd, 열린 파일에 붙는 정수 번호)**: Linux/macOS에서 0=stdin, 1=stdout, 2=stderr, 3부터는 `open()` 결과.
- **HANDLE(윈도우의 파일 디스크립터 대응, 커널 객체에 대한 포인터 비슷한 것)**: 정수지만 의미는 비슷.
- **버퍼(Buffer, 데이터를 모아뒀다 한 번에 처리하려고 쓰는 임시 저장 공간)**: I/O 성능의 핵심.
- **플러시(Flush, 버퍼에 쌓인 내용을 실제로 내보내는 동작)**: `file.flush()` 또는 `fsync`.

## 포함 관계: 내 프로그램부터 디스크까지

```
Python 코드
 └── Python 런타임 버퍼 (io.BufferedWriter)
      └── 시스템 콜 (write)
           └── 커널의 페이지 캐시 (Page Cache)
                └── 디스크 드라이버
                     └── 실제 SSD/HDD
```

**한 번의 `f.write("hi")`가 디스크 플래터에 도달하기까지 최소 4단계를 거친다.** 각 단계마다 버퍼가 있어서, 중간에 전원 나가면 아직 디스크에 도달 못 한 데이터는 날아감.

## 단계 분해: `open → read → close`가 실제로 하는 일

```python
with open("data.txt", "r") as f:
    content = f.read()
```

### 1단계: `open("data.txt", "r")`
- 유저 모드 → 커널 모드 전환
- 커널이 파일 시스템에서 해당 inode(Linux) / MFT 엔트리(NTFS) 찾음
- 권한 체크 (읽기 권한 있나?)
- 커널 내부에 "파일 테이블 엔트리" 생성
- **파일 디스크립터 정수 반환** (예: 3)

### 2단계: `f.read()`
- 커널에게 "fd=3번 파일 내용 줘" 요청
- 커널이 **페이지 캐시**에 해당 파일 있는지 먼저 확인
  - 있으면 (캐시 히트) → RAM에서 바로 복사 (빠름, μs 단위)
  - 없으면 (캐시 미스) → 디스크에서 읽어서 페이지 캐시에 올리고 복사 (느림, ms 단위)
- 유저 공간 메모리로 데이터 복사
- **같은 파일 두 번째 읽기는 훨씬 빠른 이유가 이 페이지 캐시 때문**

### 3단계: `close()`
- 파일 테이블 엔트리 해제
- fd 번호 회수
- 쓰기 모드였다면 커널 버퍼 플러시 시도

## 파일 디스크립터 vs HANDLE 비교표

| 관점 | 파일 디스크립터 (Linux/macOS) | HANDLE (Windows) |
|---|---|---|
| **타입** | `int` | `void*` (정수지만 포인터로 취급) |
| **표준 값** | 0=stdin, 1=stdout, 2=stderr | `GetStdHandle(STD_INPUT_HANDLE)` 등 |
| **최대 개수** | `ulimit -n` (보통 1024~65535) | 시스템 리소스 한계 |
| **대응 API** | `open()`, `read()`, `write()` | `CreateFile()`, `ReadFile()`, `WriteFile()` |
| **파이썬에서** | `sys.stdin.fileno()` → 0 | 내부적으로 변환해서 추상화 |

## 버퍼링 3종 비교표

| 모드 | 언제 플러시? | 기본 적용 대상 | 특징 |
|---|---|---|---|
| **무버퍼 (Unbuffered)** | 매 호출마다 즉시 | `stderr` | 느림, 하지만 손실 없음 |
| **라인 버퍼 (Line-buffered)** | `\n` 만나면 | 터미널에 연결된 `stdout` | 대화형에 적합 |
| **블록 버퍼 (Block-buffered)** | 버퍼 꽉 차면 (기본 4KB or 8KB) | 파일에 리다이렉트된 `stdout` | 빠름, 하지만 크래시 시 손실 위험 |

**AI Agent에서 자주 만나는 함정**: 스트리밍 응답 출력할 때 `print("token", end="")`로 `\n` 없이 찍으면 라인 버퍼 모드라도 버퍼에 쌓이기만 함. `flush=True` 붙여야 실시간으로 나옴.
```python
print(token, end="", flush=True)
```

## 동기 I/O vs 비동기 I/O

| | 동기 I/O | 비동기 I/O |
|---|---|---|
| **호출 직후** | 결과 나올 때까지 블로킹 | 즉시 반환, 나중에 알림 |
| **파이썬 표준** | `open()`, `read()` | `aiofiles`, `asyncio.open_connection()` |
| **디스크 I/O 효과** | 스레드 멈춤 | 다른 코루틴으로 점프 |
| **네트워크 I/O 효과** | 매우 느림 (왕복 지연) | 극적 개선 |

**중요한 함정**: 로컬 SSD 파일 읽기는 async로 바꿔도 **그렇게 안 빨라짐**. 왜냐하면 리눅스의 파일 I/O는 원래 대부분 블록킹이고, async 파일 라이브러리는 내부적으로 스레드 풀에 넘기는 수준. 진짜 성능 차이는 [[동시성과 async-await|네트워크 I/O]]에서 남.

## 파이썬 파일 열기 모드 정리

| 모드 | 의미 | 없는 파일 | 기존 내용 |
|---|---|---|---|
| `r` | 읽기 (기본) | 에러 | 유지 |
| `w` | 쓰기 | 생성 | **지움** |
| `a` | 추가 | 생성 | 유지, 끝에 추가 |
| `r+` | 읽기+쓰기 | 에러 | 유지 |
| `w+` | 읽기+쓰기 | 생성 | 지움 |
| `x` | 독점 생성 | 생성 | **있으면 에러** (경쟁 상태 방지) |
| `b` | 바이너리 (조합용) | - | - |
| `t` | 텍스트 (기본) | - | - |

**텍스트 모드(`t`)는 인코딩 + 줄바꿈 변환 포함**: Windows에서 `w`로 열면 `\n` → `\r\n`으로 자동 변환됨. 바이너리 파일을 `t` 모드로 열면 깨짐. 이미지/PDF/모델 가중치는 반드시 `rb`/`wb`.

## 일상 비유

- **파일 I/O = 택배 주문**: 내가 직접 창고 가는 게 아니라 주문서(시스템 콜) 넣으면 기사(커널)가 가져다줌.
- **버퍼 = 택배 집하장**: 매번 한 개씩 배송하면 비효율이라 집하장에 모아서 한 번에 보냄.
- **페이지 캐시 = 가까운 물류창고**: 한 번 시킨 건 근처 창고에 뒀다가 다음 주문 때 빠르게 꺼내줌.
- **플러시 = "지금 당장 보내주세요"**: 집하 대기 중인 물건도 바로 출하.

## 직접 확인해 보기

### 1. 버퍼링 체감
```python
import time

with open("test.txt", "w") as f:
    f.write("line1\n")
    time.sleep(5)
    # 이 5초 동안 다른 터미널에서 `cat test.txt` 해보면
    # 블록 버퍼 모드라 아무것도 안 보임
    f.write("line2\n")
# with 블록 끝나고 close() 되면 그제서야 디스크에 반영
```

### 2. 열린 파일 디스크립터 개수
```python
import os
print(len(os.listdir(f"/proc/{os.getpid()}/fd")))  # Linux/WSL
# 3~5개 나옴 (stdin, stdout, stderr + 기본 몇 개)
```

### 3. Windows: 프로세스가 열고 있는 파일
Sysinternals `handle.exe` 또는 Resource Monitor → CPU 탭 → 관련 핸들

### 4. 캐시 히트 체감
```bash
# Linux
echo 3 | sudo tee /proc/sys/vm/drop_caches   # 페이지 캐시 비우기
time cat huge_file.bin > /dev/null   # 첫 번째: 느림
time cat huge_file.bin > /dev/null   # 두 번째: 10배 이상 빠름
```

## AI Agent 개발에서 주의점

### 1. 로그 실시간 확인 안 됨
```python
# 나쁨: 프로세스 죽어야 로그 보임
with open("agent.log", "a") as f:
    f.write(f"{event}\n")

# 좋음: 매번 플러시
with open("agent.log", "a", buffering=1) as f:  # 라인 버퍼
    f.write(f"{event}\n")
```

### 2. 파일 디스크립터 누수
```python
# 나쁨: 예외 터지면 닫히지 않음
f = open("big.json")
data = json.load(f)  # 여기서 에러 나면 fd 누수
f.close()

# 좋음: with로 자동 정리
with open("big.json") as f:
    data = json.load(f)
```
fd는 프로세스당 한계가 있어서(보통 1024) 누수 쌓이면 `Too many open files` 터짐. [[동시성과 async-await|async]]로 병렬 요청 많이 띄우면 자주 만남.

### 3. 대용량 파일은 스트리밍
```python
# 나쁨: 10GB 로그 전부 메모리로
with open("huge.log") as f:
    lines = f.readlines()   # [[메모리 구조|Heap]] 폭발

# 좋음: 한 줄씩 읽음
with open("huge.log") as f:
    for line in f:          # 내부적으로 버퍼 단위 읽기
        process(line)
```

### 4. 동시 쓰기 주의
여러 [[프로세스 vs 스레드|프로세스/스레드]]가 같은 파일에 쓰면 섞임. 로그는 한 프로세스만 쓰게 하거나 `logging` 모듈의 `QueueHandler` 사용.

## 왜 버퍼를 두 겹이나 쓰나

- **시스템 콜이 비싸서**: 유저→커널 모드 전환에만 수 μs 소요. 한 바이트마다 write 호출하면 디스크 느린 게 문제가 아니라 모드 전환만으로 죽음.
- **디스크 I/O는 블록 단위**: SSD도 4KB 블록으로 움직임. 1바이트 쓰려고 4KB 읽고 고쳐서 다시 4KB 쓰는 구조라, 한 번에 4KB 모아 쓰는 게 훨씬 효율적.
- **페이지 캐시로 디스크 왕복 줄이기**: 반복 읽기는 RAM에서 처리. `free -h` 해보면 `buff/cache` 영역이 이것.

## 한마디 요약
**파일 I/O는 커널에게 대행 시키는 행위. 버퍼가 성능 올려주지만 실시간성이 필요하면 `flush=True` 잊지 말기. 대용량은 무조건 스트리밍.**
