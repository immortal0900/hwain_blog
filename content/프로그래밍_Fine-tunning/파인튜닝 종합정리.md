# 파인튜닝 종합 정리 (기초 → SOTA)

기존 3개 노트(`기초 사전지식`, `최신 사전지식`, `최신 SOTA 방법`)를 한 흐름으로 통합. 중복 제거, 분류 재구성.

---

## 1. 숫자 표현 형식 (Precision)

컴퓨터는 모든 수를 비트(0/1)로 저장한다. `32`, `16`, `4`는 **숫자 하나를 몇 비트로 표현하는가**의 약속이다. AI 가중치는 `0.00231` 같은 소수점 값이 대부분이므로 정수형이 아닌 **float(부동소수점)** 형식을 쓴다.

16비트는 두 파트로 나뉜다.
- **지수부(exponent)** → 숫자의 **범위** 담당
- **가수부(mantissa)** → 숫자의 **정밀도** 담당

| 형식 | 비트 | 특징 | 범위 | 소수점 정밀도 |
|---|---|---|---|---|
| **float32** | 32 | 표준, 메모리 큼 | 약 3.4×10³⁸ | 약 7자리 |
| **float16** | 16 | 가수부↑, 지수부↓ | 약 65,504 (좁음) | 약 3자리 |
| **bfloat16** | 16 | 지수부↑, 가수부↓ | float32와 동일 | 3자리보다 낮음 |

### Overflow와 NaN (float16의 약점)
학습 중 수만 번의 곱·덧셈이 반복되며 값이 float16 한계치(65,504)를 넘으면 `inf`로 변하고, `inf`에 연산이 더해지면 결국 `NaN`으로 학습이 망가진다. bfloat16은 **범위가 float32와 같아 터지지 않는다** → 정밀도가 약간 떨어져도 LLM 학습에선 bfloat16이 표준이 된 이유다.

## 2. 양자화 (Quantization)

### 양자화 오차 — "4비트 눈금에 맞춤"
- 원본(32비트): `5.1234567` 같은 매우 정밀한 값
- 4비트 세계: 눈금 `2⁴ = 16`개뿐. 예: `0, 0.6, 1.2, ..., 5.1, 5.7, ..., 10`
- 저장 시 가장 가까운 눈금(`5.1`)에 맞춰짐 → **사라진 `0.0234567`은 복원 불가**

즉 압축 해제해도 정보가 되살아나지 않는다.

### 일반 4비트 vs NF4 (Normal Float 4)
| 구분 | 일반 4비트(INT4, RTN) | **NF4** |
|---|---|---|
| 눈금 방식 | 일정 간격 | **정규 분포에 맞춰 0 근처는 촘촘, 끝은 듬성** |
| 이유 | — | AI 가중치는 대부분 0 근처에 몰려 있음 |
| 결과 | 중요한 미세값 뭉개짐 → 지능 하락 | 같은 4비트로 **핵심 정보 보존** |
| 용도 | 주로 추론용 | **학습까지 가능** (QLoRA와 결합) |

### 계산 시 왜 32비트가 아닌 bfloat16으로 복원하나?
"그릇이 크면 좋은 거 아니냐"는 오해에 대한 답.
1. **속도**: A100/H100 Tensor Core에서 bfloat16이 float32보다 2~8배 빠름
2. **대역폭**: 내부 데이터 통로(Bandwidth)가 한정적 → 이미 4비트로 뭉개진 값을 32비트로 실어나르는 건 낭비
3. **충분함**: 어차피 4비트 수준 정보라 bfloat16 정밀도면 다 담김

## 3. PEFT (Parameter-Efficient Fine-Tuning)

전체 파라미터를 건드리지 않고도 성능을 내는 기법군.

### LoRA → QLoRA → DoRA
- **LoRA**: 원본 가중치는 동결하고 옆에 얇은 어댑터만 학습
- **QLoRA (Quantized LoRA)**: **NF4로 압축한 본체 + LoRA 어댑터**. RTX 4090 한 장으로 7B~9B 모델 파인튜닝 가능
  - 비유: 요약본(NF4)은 그대로 두고 포스트잇(LoRA)으로 새 내용 추가
- **DoRA (Weight-Decomposed LoRA)**: 가중치를 **크기(Magnitude)와 방향(Direction)으로 분해**해 학습. LoRA보다 적은 파라미터로 Full Fine-tuning에 근접

> `load_in_4bit=True` + `bnb_4bit_quant_type="nf4"` = "가장 똑똑한 눈금(NF4)으로 압축해 학습(QLoRA)하겠다"는 선언

### Unsloth — "엔진 튜닝"
**2026년 개인용 GPU 파인튜닝 사실상 표준.**

- **문제 인식**: 순정 PyTorch/HuggingFace는 범용성 위주 → 계산 단계마다 GPU 메모리에 썼다 읽는 오버헤드
- **해법: 커스텀 커널 (OpenAI Triton 기반)** — 수십 단계 연산을 **하나의 거대 커널로 합쳐** 중간 저장 없이 한 번에 계산
- **효과**: 학습 속도 **2배 이상**, VRAM 사용량 **최대 70~80% 감소**, 정확도 손실 0%
- **역전파 최적화**: 불필요한 중간값을 저장하지 않고 실시간 재계산해 메모리 절감

HuggingFace의 **TRL(Transformer Reinforcement Learning)** 라이브러리와 병행해 쓰는 것이 현재 표준 스택.

## 4. 학습 효율화 기법

### Packing — "빈 공간 없이 꽉꽉 채우기"
- 일반 방식: max_len=512일 때 100단어 문장 넣으면 나머지 412칸을 **0(Padding)**으로 채움 → 0도 연산하므로 VRAM·연산 낭비
- Packing: 여러 짧은 대화를 이어 붙여 한 샘플에 채움
  - 형식: `[대화1] <|endoftext|> [대화2] <|endoftext|> [대화3] ...`
- **효과**: 학습 속도 **2~5배**

### Flash Attention 2
긴 문맥(long context) 처리 시 어텐션 연산을 물리적으로 가속. 사실상 필수 알고리즘.

## 5. 정렬(Alignment) / Post-training SOTA

모델을 **지시 잘 따르고 안전하게** 만드는 단계. RLHF의 무거움을 벗어나 '단순·고효율'로 진화 중.

### 흐름: RLHF → DPO → ORPO/SimPO/BPO
- **RLHF (기존)**: 보상 모델 + 강화학습(PPO). 복잡하고 불안정
- **DPO (Direct Preference Optimization)** — 현재 주류
  - 쌍 데이터(Winner, Loser)만 주면 모델이 정답 쪽 확률을 스스로 높임
  - 보상 모델 불필요
- **ORPO (Odds Ratio Preference Optimization)**
  - 기존: SFT(정답 배우기) → DPO(선호 학습) **2단계**
  - ORPO: **SFT와 선호 학습을 한 번에**. 정답 형식을 배우면서 "이렇게 답하면 감점" 신호를 동시에 받음 → 시간 단축 + 품질 상승
- **BPO (Balanced Preference Optimization)**
  - DPO가 Rejected 답변 억제에 치중해 전체 품질이 떨어지는 문제를 보완. 긍정/부정 최적화 **균형**
- **SimPO (Simple Preference Optimization)**
  - **참조 모델(Reference Model) 제거**. 타겟 모델 하나만으로 선호 학습 → 메모리·계산 극도 절감
- **GRPO (Group Relative Policy Optimization)**
  - DeepSeek-V3 등에서 사용해 화제
  - **보상 모델 없이 그룹 내 상대 비교**로 강화학습 → PPO보다 가볍고 안정적. 추론 능력 향상에 강함

## 6. 구조적 최적화 / 신규 접근

- **MoE (Mixture of Experts) 파인튜닝**: 특정 Expert 레이어만 선택적으로 튜닝해 도메인 지식(의료·법률 등)을 빠르게 주입
- **Knowledge Distillation (지식 증류)**: GPT-4 등 거대 모델의 추론 과정을 작은 모델(Llama-3 8B 등)에 학습 → 체급 대비 강력
- **다중 모델 앙상블 (PLM + LLM)**: 단일 LLM의 한계 보완
  - **PLM (KoELECTRA 등, 분류 특화)**: "피싱일 확률"을 통계적으로 계산
  - **LLM (Gemma 등, 생성·추론 특화)**: "왜 피싱인지" 논리적 근거 생성
  - 두 점수를 평균 내어 오탐지율 ↓

## 7. 추론 엔진 — vLLM

학습이 끝난 모델을 **서비스**에 올릴 때 단순 로드보다 전용 엔진이 몇 배 빠르다.

### 핵심 원리: PagedAttention
운영체제의 '가상 메모리' 개념을 AI에 도입.
- **기존**: 문장이 길수록 KV Cache가 늘어 메모리를 **미리 크게 예약** → 낭비 60~80%
- **vLLM**: 메모리를 페이지 단위로 쪼개 **필요한 만큼만 동적 할당** → 남는 공간에 더 많은 사용자 요청 동시 처리

### 효과
1. **처리량(Throughput)**: 동시 응답 가능 사용자 수 2~4배
2. **비용 절감**: 서버 4대 → 1대
3. **지연 단축**: TTFT(첫 토큰 응답)·전체 생성 속도 개선

### 사용 방식
vLLM은 내부에 **FastAPI 기반 자체 서버**를 포함.

**① 자체 API 서버 (간단, 대체)**
```bash
python -m vllm.entrypoints.openai.api_server
```
OpenAI 규격(`/v1/chat/completions`) 자동 제공 → 그냥 API만 빨리 외부에 열고 싶을 때.

**② FastAPI와 협력 (커스텀 로직)**
예: KoELECTRA 점수 + Gemma 점수 합산 같은 복합 로직이 필요하면
1. 직접 FastAPI 서버를 작성
2. 그 안에서 vLLM을 **엔진(라이브러리)**으로 불러옴
3. 흐름: `입력 → KoELECTRA 계산 → vLLM으로 Gemma 추출 → 점수 합산 → 응답`

## 8. 한눈에 보는 SOTA 비교표

| 카테고리 | 기법 | 특징 | 추천 상황 |
|---|---|---|---|
| **효율성** | DoRA | LoRA보다 정교한 가중치 조정 | 고정확도 전문 도메인 |
| **속도/메모리** | Unsloth | 학습 2배↑, 정확도 손실 0% | 실험 반복이 잦을 때 |
| **압축** | QLoRA + NF4 | 4비트 + 어댑터 학습 | 소비자 GPU로 대형 모델 |
| **데이터 효율** | Packing | 패딩 제거, 2~5배 | 짧은 대화 데이터 多 |
| **정렬(주류)** | DPO | 쌍 데이터 기반, 보상모델 X | 일반 선호 학습 |
| **정렬(통합)** | ORPO | SFT+DPO 동시 | 2단계가 부담될 때 |
| **정렬(초경량)** | SimPO | 참조 모델 제거 | 리소스 극도 제한 |
| **정렬(추론)** | GRPO | 그룹 상대 비교 RL | 복잡한 추론 이행 |
| **도메인 주입** | MoE FT | Expert만 튜닝 | 도메인 특화 지식 |
| **소형화** | Knowledge Distillation | 큰 모델 → 작은 모델 | 체급 대비 성능 극대 |
| **추론(서빙)** | vLLM / PagedAttention | 처리량 2~4배 | 프로덕션 서빙 |

## 9. 구현 스니펫 (Unsloth + NF4)

```python
from unsloth import FastLanguageModel
import torch

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "google/gemma-2-9b", # 사용할 모델
    max_seq_length = 2048,            # 최대 문장 길이
    load_in_4bit = True,              # NF4 4비트 양자화
    dtype = None,                     # 지원 타입 자동(보통 bf16)
)
```

- `load_in_4bit=True` + NF4 = **QLoRA 방식 학습 준비**
- `dtype=None` → 하드웨어가 지원하는 최적 dtype(주로 bfloat16) 자동 선택
