Retriever의 성능은 **"사용자의 질문 의도와 키워드를 얼마나 정확하게 잡아내느냐(정확도)"**를 기준으로 나뉩니다.

단순히 DB에서 꺼내오는 것을 넘어, **검색 결과를 재조정(Reranking)**하거나 **검색 방식을 섞는(Hybrid)** 기술이 들어갈수록 성능이 압도적으로 좋아집니다.

---

### 🏆 Retriever 성능 계급도 (정확도 기준)

#### 1위: Hybrid Search + Reranker (👑 현존 RAG의 끝판왕)

> **"키워드와 의미를 다 잡고, AI가 채점까지 다시 함"**

- **방식:**
    
    1. **벡터 검색(의미)**과 **키워드 검색(단어)**으로 후보군을 넓게(예: 50개) 가져옵니다.
        
    2. **Reranker(재순위화 모델)**라는 별도의 AI가 이 50개를 하나하나 읽어보고 "이게 진짜 질문에 맞는 답인가?"를 채점해서 1등부터 다시 줄 세웁니다.
        
- **장점:** 정확도가 가장 높습니다. 벡터 검색의 멍청함(키워드 불일치)과 키워드 검색의 한계(의미 파악 불가)를 모두 극복합니다.
    
- **단점:** Reranker를 돌리는 비용과 시간(Latency)이 추가로 듭니다.
    
- **추천 도구:** `Cohere Rerank`, `BGE-Reranker`, `LangChain ContextualCompressionRetriever`
    

#### 2위: Hybrid Search (Ensemble Retriever)

> **"벡터와 키워드의 장점만 섞음 (가성비 최강)"**

- **방식:** **BM25(키워드 검색)**와 **Vector(의미 검색)** 결과를 가져와서 가중치를 섞습니다. (예: 벡터 50% + 키워드 50%)
    
- **장점:** Reranking 모델을 안 돌려도 되므로 빠르면서도, 단순 벡터 검색보다 훨씬 정확합니다. 업계 표준으로 자리 잡고 있습니다.
    
- **단점:** 가중치 조절(파라미터 튜닝)이 필요합니다.
    
- **추천 도구:** `LangChain EnsembleRetriever`
    

#### 3위: Parent Document Retriever (or Multi-Vector)

> **"검색은 작은 조각으로, 답변은 큰 문맥으로"**

- **방식:** 문서를 아주 잘게 쪼개서(Small Chunk) 검색 정확도를 높입니다. 하지만 LLM에게 줄 때는 그 잘게 쪼갠 조각의 **부모 문서(원래 문단, Large Chunk)**를 통째로 줍니다.
    
- **장점:** 검색은 예리하게 하고, 답변은 문맥을 파악해서 풍성하게 합니다. "앞뒤 내용이 짤려서 답변이 이상해지는" 현상을 막습니다.
    
- **추천 도구:** `LangChain ParentDocumentRetriever`
    

#### 4위: Multi-Query Retriever

> **"질문을 여러 개로 뻥튀기해서 검색"**

- **방식:** 사용자가 "전세 대출 조건"이라고 물으면, LLM이 알아서 "전세 자금 대출 금리", "전세 대출 한도", "전세 대출 자격" 등으로 질문을 3~5개 변형해서 다 검색해옵니다.
    
- **장점:** 사용자가 질문을 대충 해도 AI가 찰떡같이 알아서 다양한 각도로 찾아줍니다.
    
- **단점:** 검색을 여러 번 하므로 속도가 느려질 수 있습니다.
    

#### 5위: Standard Vector Search (Dense Retrieval)

> **"가장 기본, 그러나 한계가 명확함"**

- **방식:** 우리가 흔히 아는 임베딩(Cosine Similarity) 검색입니다.
    
- **장점:** 구축이 쉽고 빠릅니다.
    
- **단점:** "전문 용어", "고유 명사(사람 이름, 제품명)" 검색에 매우 취약합니다. (예: '아이폰15'를 검색했는데 '스마트폰' 관련 엉뚱한 글이 나올 수 있음)

### 💡 개발자를 위한 추천 로드맵

1. **초기 단계:** 그냥 **Basic Vector Search** (`VectorStoreRetriever`)로 빨리 만듭니다.
    
2. **문제 발생:** "사용자가 정확한 용어를 쳤는데 못 찾네?"
    
3. **1차 업그레이드:** **Hybrid Search** (`EnsembleRetriever`)로 바꿉니다. (BM25 추가)
    
4. **2차 업그레이드:** "찾긴 찾았는데 1등 결과가 좀 이상해."
    
5. **최종 진화:** **Reranker**를 붙여서 상위 5개만 다시 추려냅니다. (`ContextualCompressionRetriever` + `Cohere/BGE`)
    

이 순서대로 고도화하시는 것이 가장 효율적입니다.

### 💡 왜 Graph RAG(Neo4j)가 사기급인가? (예시)

만약 **"김철수 부장이 횡령한 금액과 공모자는?"**이라는 질문을 했다고 가정해 봅시다.

- **일반 Retriever (Vector/Hybrid):**
    
    - 문서에서 "김철수", "횡령"이라는 단어가 들어간 문단을 찾습니다.
        
    - 만약 문서 A에 "김철수 10억 횡령", 문서 B에 "김철수의 친구 이영희"라고 따로 적혀 있다면, **이영희가 공모자인지는 찾아내지 못할 확률이 높습니다.** (문맥이 끊겨 있으니까요)
        
- **Graph RAG:**
    
    - 그래프 DB에는 이미 `(김철수)-[친구]->(이영희)`, `(김철수)-[혐의]->(횡령)` 처럼 연결이 되어 있습니다.
        
    - 검색 시 **"김철수와 연결된 사람(2-depth)을 다 가져와"**라고 쿼리를 날립니다.
        
    - 문서에 직접적으로 "이영희가 공모했다"는 말이 없어도, **관계망을 통해 정황을 찾아냅니다.**
        

### 📊 최종 선택 가이드

1. **"법률, 의학, 범죄 수사, 복잡한 사내 규정" 시스템이다.**
    
    - 👉 **Graph RAG (Neo4j) 필수**입니다. 정보의 **"정확성"**과 **"관계 추론"**이 생명이니까요.
        
2. **"그냥 고객 상담 챗봇, 매뉴얼 Q&A, 사내 위키 검색" 수준이다.**
    
    - 👉 **Hybrid Search + Reranker**로 충분합니다. Graph RAG는 과유불급(Over-engineering)일 수 있습니다.
        
3. **"전체 문서를 아우르는 트렌드 리포트를 써야 한다."**
    
    - 👉 **Microsoft GraphRAG** (Community Summary 방식)를 쓰세요.
        

**결론적으로, 돈과 시간이 무제한이라면 `Graph RAG + Vector Hybrid + Reranker`를 섞어 쓰는 것이 현재 기술상의 정점(State-of-the-Art)입니다.**

# Dense Retriever와 FAISS

FAISS는 모델이 아니라 **'검색 엔진'**에 가깝습니다.

| **구분**    | **Dense Retriever (밀집 검색기)**                                       | **FAISS (Facebook AI Similarity Search)**                                        |
| --------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| **정의**    | 텍스트를 **벡터(숫자 리스트)로 변환**하고 검색하는 **'방법론'** 또는 **'모델'**               | 변환된 벡터들을 저장하고 **유사한 것을 빨리 찾아주는 '라이브러리(도구)'**                                     |
| **핵심 역할** | **의미 파악 (Understanding)**<br><br>  <br><br>문장의 뜻을 이해하여 벡터 공간에 배치함. | **고속 연산 (Indexing & Search)**<br><br>  <br><br>수백만 개의 벡터 중 가장 가까운 것을 0.1초 안에 찾음. |
| **기술 기반** | Deep Learning 모델 (BERT, RoBERTa, DPR 등)                            | 수학적 알고리즘 (ANN, L2 거리, 내적 등)                                                      |
| **비교 대상** | Sparse Retriever (BM25, TF-IDF: 키워드 기반 검색)                         | ChromaDB, Pinecone, Weaviate (다른 벡터 DB들)                                         |

| **검색 방식**                                    | **장점 (특기)**                                                                 | **단점 (약점)**                                                                               |
| -------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **Dense Retriever**<br><br>  <br><br>(의미 기반) | **"의미 파악"**<br><br>  <br><br>'스마트폰'이라고 검색해도 '갤럭시', '아이폰'을 찾아냄. (동의어 처리에 강함) | **"정확한 키워드"**<br><br>  <br><br>고유 명사, 제품 번호(예: 'RTX 4090'), 전문 용어 검색 시 엉뚱한 결과를 내놓을 때가 있음. |
| **BM25**<br><br>  <br><br>(키워드 기반)           | **"정밀 타격"**<br><br>  <br><br>사용자가 입력한 단어가 반드시 포함된 문서를 찾음. (제품명, 이름 검색에 강함)  | **"문맥 무시"**<br><br>  <br><br>단어가 조금만 달라도 못 찾음. (예: '휴대폰'으로 검색하면 '스마트폰' 문서를 못 찾을 수 있음)     |
### 2. 현재 구성(Supabase + pgvector)의 압도적 장점

FAISS를 따로 쓰는 것보다 지금 구성이 훨씬 강력한 이유가 있습니다. 바로 **"메타데이터 필터링(Metadata Filtering)"** 때문입니다.

- **FAISS만 쓸 경우:**
    
    - 벡터(숫자)만 저장합니다.
        
    - "2024년에 작성된 문서 중에서 검색해줘" 같은 조건 검색이 매우 까다롭습니다. (벡터 검색 후 ID를 매핑해서 다시 DB 조회 필요)
        
- **PostgreSQL (pgvector)를 쓸 경우:**
    
    - 벡터와 일반 데이터(작성일, 작성자, 카테고리 등)가 한 테이블에 있습니다.
        
    - **SQL 한 줄**로 "필터링"과 "벡터 유사도 검색"을 동시에 할 수 있습니다. 이것은 RAG 시스템 구축 시 엄청난 이점입니다.

# MTEB(Massive Text Embedding Benchmark) 리더보드는 텍스트 임베딩 모델의 성능을 평가하는 가장 공신력 있는 지표
 https://huggingface.co/spaces/mteb/leaderboard

공유해주신 Hugging Face의 **MTEB (Massive Text Embedding Benchmark)** 리더보드는 텍스트 임베딩 모델(문장을 벡터 숫자로 변환하는 모델)들의 성능을 다양한 작업에서 평가하고 순위를 매긴 표입니다.

각 컬럼의 의미를 알기 쉽게 해석해 드리겠습니다.

### 1. Mean (평균 점수)

가장 중요한 지표입니다. **"Mean"은 해당 모델이 수행한 모든 테스트 항목(Classification, Clustering, Retrieval 등) 점수의 평균값**을 의미합니다.

- 이 점수가 높을수록 특정 분야뿐만 아니라 전반적으로 성능이 우수한 '육각형 모델'에 가깝다고 볼 수 있습니다.
    

### 2. 성능 평가 컬럼 (Task Categories)

모델이 실제로 어떤 일을 잘하는지 보여주는 항목들입니다. 각 숫자는 100점 만점 환산 점수입니다.

- **Retrieval (정보 검색)**: 사용자의 질문에 대해 가장 적절한 문서를 찾아내는 능력입니다.
    
    - _활용_: RAG(검색 증강 생성) 시스템이나 사내 검색 엔진을 만들 때 가장 중요한 지표입니다.
        
- **STS (Semantic Textual Similarity, 의미적 텍스트 유사도)**: 두 문장의 의미가 얼마나 비슷한지(0~1)를 얼마나 정확하게 측정하는지 평가합니다.
    
    - _활용_: "배고파"와 "식사하고 싶어"를 같은 의미로 인식해야 할 때 쓰입니다.
        
- **Clustering (군집화)**: 비슷한 주제나 내용을 가진 문장끼리 얼마나 잘 묶어주는지 평가합니다.
    
    - _활용_: 뉴스 기사 자동 분류, 고객 리뷰 유형별 그룹화 등에 쓰입니다.
        
- **Classification (분류)**: 임베딩된 문장만으로 감정 분석(긍정/부정)이나 카테고리 분류를 얼마나 잘 수행하는지 봅니다.
    
- **PairClassification (쌍 분류)**: 두 문장이 서로 관련이 있는지 없는지(이진 분류)를 판단하는 능력입니다.
    
    - _활용_: 중복 질문 탐지 등에 유용합니다.
        
- **Reranking (재순위화)**: 이미 검색된 결과들을 다시 검토하여, 가장 관련성 높은 순서대로 정렬하는 능력입니다.
    
- **Summarization (요약)**: 기계가 생성한 요약문이 인간이 쓴 요약문과 얼마나 유사한지(벡터 거리)를 통해 평가합니다.
    
- **BitextMining**: 두 언어(예: 한국어-영어)로 된 텍스트 중에서 서로 번역 관계인 문장 쌍을 찾아내는 능력입니다.
    

### 3. 모델 스펙 컬럼 (Model Specifications)

성능 외에 모델의 물리적인 특징을 나타냅니다.

- **Model Size / Params**: 모델의 크기(파라미터 수)입니다. 보통 크기가 클수록 성능이 좋지만, 메모리를 많이 차지하고 속도가 느려집니다.
    
- **Embedding Dimensions**: 문장을 변환했을 때 나오는 벡터의 길이(차원 수)입니다.
    
    - _주의_: 차원이 높을수록(예: 4096) 정보량은 많지만, 벡터 DB 저장 비용이 비싸집니다. (보통 768, 1024 등을 많이 씀)
        
- **Max Tokens**: 한 번에 처리할 수 있는 문장의 최대 길이입니다. 긴 문서를 처리해야 한다면 이 수치가 높은 모델을 써야 합니다.
    
- **Memory Usage**: 모델을 돌리기 위해 필요한 실제 메모리(VRAM/RAM) 용량입니다.
    

**요약하자면:** 가장 먼저 **Mean(평균)** 점수로 대략적인 순위를 보시고, 만들고자 하는 서비스가 **검색(Retrieval)** 위주인지, **분류(Classification)** 위주인지에 따라 해당 컬럼 점수가 높은 모델을 선택하시는 것이 좋습니다.

| 모델                            | MTEB 점수              | 파라미터 수 | 최대 토큰 길이 | 임베딩 차원       |
| ----------------------------- | -------------------- | ------ | -------- | ------------ |
| Qwen3-Embedding-8B            | 70.58(다국어 1위)        | 8B     | 32,768   | 최대 4096 (가변) |
| multilingual-e5-base          | large=64.0<br>small= | 278M   | 512      | 768          |
