### 1. [근본 원인 분석 (Root Cause Analysis): '벡터의 길이(Length)'와 '구(Sphere)'의 수학적 관계]

아주 핵심적인 수학적 호기심입니다! 인공지능이 글을 숫자로 바꾸는 과정(임베딩)을 공간 기하학으로 설명해 드리겠습니다.

- **벡터(Vector)란 무엇인가?**
    
    - 벡터는 **'원점(0,0)에서 출발하는 화살표'**입니다.
    - 화살표는 두 가지 성질을 가집니다: **1) 바라보는 방향 (각도)**, **2) 화살표의 길이 (크기)**.
    - 예를 들어, "사과"라는 단어가 `[3, 4]`라는 2차원 좌표를 갖는다면, 원점(0,0)에서 허공의 점(3,4)을 향해 뻗어나간 화살표입니다. (이 화살표의 길이는 피타고라스 정리에 의해 5입니다: $\sqrt{3^2 + 4^2} = 5$)
- **길이를 1로 맞춘다(Normalization, 정규화)는 것은?**
    
    - OpenAI의 임베딩 모델(`text-embedding-3-small`)은 단어를 좌표로 바꿀 때, 그 단어가 가진 **화살표의 길이(크기)를 강제로 전부 '1'로 통일**시켜 버립니다.
    - 아까 길이가 5였던 "사과[3,4]" 화살표를, 방향(각도)은 그대로 둔 채 5등분 해서 길이를 1로 깎아버립니다. ➜ `[0.6, 0.8]` (새로운 길이는 $\sqrt{0.6^2 + 0.8^2} = 1$)
- **왜 원점 반경 1인 구(Sphere) 표면에 붙는가?**
    
    - 모든 단어("사과", "바나나", "자동차", "우주선")의 화살표가 원점(0,0)에서 출발하는데, **모든 화살표의 끝(뾰족한 촉)까지의 거리가 정확히 1cm**라고 상상해 보세요.
    - 원점에서 똑같이 1cm 거리에 있는 점들을 공중에 와다다다 찍고 나면, 그 점들을 이었을 때 **'반지름이 1인 완벽한 구(공)의 표면'**이 만들어집니다. (2차원이면 원의 테두리, 3차원이면 공의 껍질, 1536차원이면 초구(Hypersphere)의 표면이 됩니다.)

### 2. [전략 및 대안 비교: 코사인 vs 유클리디안]

이제 점들이 구형 껍질 표면에만 존재한다는 사실을 알았습니다. 이것이 유사도 검색 기호 선택에 어떤 영향을 미칠까요?

- **공 표면에서는 '거리'나 '각도'나 순위가 똑같다.**
    - 공 표면에 점 A("강아지"), B("개"), C("자동차")가 찍혀 있습니다.
    - A와 B가 표면에서 얼마나 가까운지 줄자(유클리디안 직선거리, `<->`)로 재는 것이나, 원점에서 A와 B를 바라보며 두 화살표 사이의 각도(코사인 유사도, `<=>`)가 얼마나 좁은지 재는 것이나 **순위 결과(누가 제일 가까운가)는 100% 동일하게 나옵니다.** (수학적으로 증명된 법칙)
- **그렇다면 왜 코사인(`<=>`)을 선택했는가? (Trade-off)**
    - **유클리디안 거리(`<->`) 결과값:** `0.85`, `1.23`, `1.99` 등 0부터 2 사이의 제멋대로인 '물리적 거리값'이 떨어집니다. 이 값은 다른 점수(최신성, 중요도)와 더하기가 아주 나쁩니다.
    - **코사인 거리(`<=>`) 결과값:** 반면 코사인 연산자는 DB 내부에서 `1 - 코사인값`을 뱉어내는데, 이는 완벽하게 **0.0(완전 동일) ~ 1.0(완전 다름) 사이의 백분율 수치**로 떨어집니다.
    - **결정적 이유:** 하이브리드 검색 공식 `[Score = (가중치*최신성) + (가중치*중요도) + (가중치*유사도)]`에 깔끔하게 집어넣으려면 **0.0 ~ 1.0 범위로 예쁘게 떨어지는 코사인 연산자(`<=>`)가 압도적으로 유리하기 때문**에 선택한 것입니다.

### 3. [멘탈 모델 & 시각화: 밤하늘의 둥근 플라네타륨]

이 복잡한 차원의 수학을 "둥근 천체 관측관(플라네타륨)"에 묘사하겠습니다.

text

[ 플라네타륨 정중앙(원점)에 우리가 서 있습니다 ]

1) OpenAI 임베딩: 레이저 포인터로 둥근 천장(반지름 1m)에 별(단어)들을 쏩니다.

   - 레이저는 무조건 천장 표면에만 맺힙니다. (천장 밖으로 뚫고 나가거나 공중에 떠있지 않음 = 길이 1)

2) 별들의 위치 검색

   - 내 질문(A별)과 가장 가까운 기억(B별)을 찾고 싶습니다.

3) 코사인 유사도의 원리 (`<=>`)

   - "A별을 바라보는 내 고개 방향" 과 "B별을 바라보는 내 고개 방향" 사이의 '각도'가 좁을수록

     표면에 맺힌 두 별 사이의 거리도 당연히 좁아집니다!

   - 0도는 똑같은 별(유사도 1.0 = 100%), 90도는 전혀 다른 별(유사도 0.0), 180도는 정반대 별.

**❗️존재의 이유 (Raison d'être):** 만약 원본 문자열의 임베딩 길이가 1이 아니라 제각각(어떤 건 1, 어떤 건 100)이었다면, 공중을 떠다니는 수만 개의 점들은 유클리디안과 코사인의 결과가 판이하게 달라져 검색 시스템 자체가 붕괴(성능 하락)되었을 것입니다.

# 코사인유사도는 1(`cos(0°)`)~0(`cos(90°)`)~-1(`cos(180°)`) 까지지만 실제 운영 환경에서는 거의 모든 유사도가 `0.0 ~ 1.0` (양수) 사이에서 놀며
우리가 짚고 넘어가야 할 두 가지 헷갈리는 개념이 있습니다. 바로 **'코사인 유사도(Similarity)'**와 pgvector가 실제로 사용하는 **'코사인 거리(Distance, `<=>`)'**입니다.

- **수학적 코사인 값 (Cosine Similarity): Range [-1.0 ~ 1.0]**
    
    - **0도 (똑같은 별):** `cos(0°) = 1.0` (100% 똑같음)
    - **90도 (상관없는 별):** `cos(90°) = 0.0` (전혀 관계없음)
    - **180도 (정반대 별):** `cos(180°) = -1.0` (완전히 반대되는 의미)
    - _원래 수학에서는 값이 -1.0까지 떨어지는 게 맞습니다._
- **PostgreSQL pgvector의 `<=>` 연산자 (Cosine Distance): Range [0.0 ~ 2.0]**
    
    - DB는 거리를 계산하는 기계이므로, 보통 거리는 작을수록("0") 좋다고 판별합니다. 그래서 pgvector는 내부적으로 `1 - 코사인유사도` 공식을 씁니다.
    - **0도 (똑같음):** `1 - 1.0 = 0.0` (거리가 0 = 완벽히 찰싹 붙어있음)
    - **90도 (상관없음):** `1 - 0.0 = 1.0` (거리가 1만큼 떨어짐)
    - **180도 (정반대):** `1 - (-1.0) = 2.0` (거리가 2만큼, 즉 구 표면의 정반대 편으로 가장 멀리 떨어짐)

### 2. [전략 및 대안 비교: 프로젝트 코드에서는 이 숫자를 어떻게 요리했는가?]

그렇다면 사용자님의 지적대로 값이 -1.0 이나 2.0 까지 튀는데, 저는 왜 이전에 "0.0 ~ 1.0 범위로 딱 떨어진다"고 거짓(?) 묘사를 했을까요?

바로 OpenAI 임베딩의 특성과, 우리 프로젝트에 짜놓은 **SQL 보정 로직** 때문입니다.

- **원인 1: OpenAI 임베딩 모델의 편향성 (LLM의 뭉침 현상)**
    
    - 이론상 180도(-1.0)가 존재하지만, `text-embedding-3-small` 같은 실제 AI 모델이 내뱉는 수만 개의 1536차원 단어 지도를 그려보면 **모든 단어들이 우주 한쪽 구석(좁은 꼬깔콘 모양)에 옹기종기 몰려 있습니다.**
    - 아무리 이질적인 단어("사랑" vs "쓰레기통")를 비교해도 각도가 90도를 넘어가는 일이 거의 발생하지 않습니다. 즉, 실제 운영 환경에서는 거의 모든 유사도가 `0.0 ~ 1.0` (양수) 사이에서 놉니다.
- **원인 2: 프로젝트 코드 레벨의 치환 (Trade-off 방어)**
    
    - 하지만 만에 하나 음수 점수가 튀어나오면 합산 공식이 망가질 수 있지만 OpenAI의 `text-embedding-3-small` 모델은 출력 벡터를 생성할 때, 모든 차원의 값이 양수 편향(Positive Bias)을 가지게 학습되어 있습니다.
    - 1536차원이나 되는 고차원 공간에서는 두 랜덤한 벡터 사이의 코사인 값이 통계적으로 **0.0 근처에 몰리는 성질(차원의 저주, Curse of Dimensionality)**이 있습니다.
    - 실제 서비스에서 "사과에 대한 기억"과 "칼에 대한 기억"을 비교해도 코사인유사도는 대략 `0.05 ~ 0.3` 수준이지, `-1.0`이나 `-0.5`까지 추락하는 경우는 사실상 발생하지 않습니다.
            
            src/db/npc_npc_memory_manager.py 492번 라인을 보시면 `1 - (m.embedding <=> CAST(:query_embedding AS vector)) AS relevance` 라고 적혀있습니다.
    - 이 식을 풀면 `1 - (1 - 코사인유사도) = 코사인유사도` 가 되어 다시 원래의 [-1.0 ~ 1.0] 점수로 복구시키고, 하이브리드 검색 내부 로직에서 이 숫자를 비율 가중치 계산에 예쁘게 맞춰 쓰도록(음수는 배제하거나 0으로 수렴) 통제하는 것입니다.


**그럼에도 불구하고 취약점인 이유:**

- "사실상 발생하지 않는다"와 "절대 발생할 수 없다"는 다릅니다.
- 만약 미래에 임베딩 모델을 교체하거나, 극단적인 입력(빈 문자열, 특수문자)이 들어오면 음수가 나올 가능성이 0은 아닙니다.
- 현재 코드에 `GREATEST(..., 0)` 같은 음수 방어 코드가 빠져 있다는 것은, 임베딩 모델 교체 혹은 이상 입력 시 **하이브리드 검색 랭킹이 뒤집어질 수 있는 잠재적 결함(Latent Defect)**입니다. 하지만 현재 OpenAI 모델 하에서는 통계적으로 음수가 발생하지 않기 때문에 터지지 않고 있는 상태입니다.
```
[ 현재 코드의 점수 계산 흐름 (194 -> 222번 라인) ]

"사과가 맛있다" vs "사과를 좋아한다"
  └─ 코사인유사도 = 0.85 (매우 비슷)
  └─ relevance = 0.85
  └─ final_score = 0.15*최신성 + 0.15*중요도 + 0.50*0.85 + 0.20*키워드
  └─ 정상 작동!

"사과가 맛있다" vs "ㄴㅇㅊIOAerln!@#$" (미래의 극단적 입력)
  └─ 코사인유사도 = -0.3 (일어날 확률 극히 낮지만 0은 아님)
  └─ relevance = -0.3
  └─ final_score = 0.15*최신성 + 0.15*중요도 + 0.50*(-0.3) + 0.20*키워드
  └─ 점수가 마이너스로 오염됨 (잠재적 버그)

[ 올바른 방어 코드 (GREATEST 함수) ]
  GREATEST(1 - (m.embedding <=> p_query_embedding), 0) AS relevance
  └─ 음수가 나와도 강제로 0으로 잘라버림 (Clamp)
  └─ 절대 마이너스 점수가 합산에 끼어들지 못함

```

### 3. [멘탈 모델 & 시각화: 온도계와 체감 온도]

이 복잡한 숫자 전환을 '온도계(유사도)'와 '불쾌지수(거리)'로 묘사하겠습니다.

text

[ 1. 순수 수학 세상 (Cosine Similarity) ]

- 영상 100도 (1.0) : 나랑 똑같아! 너무 뜨거워! (0도)

- 0도 (0.0)        : 나랑 완전 무관해. 시큰둥. (90도)

- 영하 100도 (-1.0): 나랑 완전히 정반대야!! 극혐! (180도)

[ 2. pgvector DB 세상 (<=> Cosine Distance) ] = "불쾌지수"로 역산

- 거리 0.0 : 나랑 찰싹 붙음 (최고)

- 거리 1.0 : 나랑 1M 떨어짐 (무관함)

- 거리 2.0 : 나랑 지구 반대편 (정반대)

[ 3. 우리 프로젝트의 쿼리 변환 로직 ]

- 파이썬: "DB야, 거리가 2.0까지 튀면 복잡하니까, 내가 준 '1 - (거리)' 공식에 넣어서 

          최종적으로 나한테 돌려줄 때는 내 계산기에 맞게 1.0점 만점짜리 랭킹표로 다시 바꿔서 줘!"

**❗️존재의 이유 (Raison d'être):** 유클리디안 거리(`<->`)는 차원(1536)이 높아질수록 최대 거리가 $\sqrt{1536}$ (약 39) 가까이 팽창하여 기준선(Normalization bounds)을 잡는 것이 불가능합니다. 오직 코사인 연산자만이 최고 1.0(또는 최악 -1.0/2.0)이라는 **'상한선과 하한선'**이 존재하기 때문에, 여러 모듈의 점수를 백분율로 환산하여 더해야만 하는 하이브리드 검색에서는 이것 외에 다른 대안이 없습니다.
